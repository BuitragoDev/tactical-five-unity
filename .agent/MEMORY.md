## 2. Goal & core mechanics (as built)

- Simulate an NBA-like franchise career: 30 teams, 82-game season (Oct 22 → mid-April), Play-In, Playoffs (best-of-7), draft, awards, records, and infinite seasons with aging/progression.
- Player is GM, not a coach/player: picks lineups, manages contracts/salary cap, finances, staff, training, morale, and hits "advance day".
- Match outcomes decided by `GameSimulator` (possession-based, attribute-driven).

## 5. Key architectural decisions & reasons

| Decision | Reason (observed/deduced) |
|---|---|
| Single scene + `UIDocument` screens, `ScreenManager` toggling `SetActive` | All UI in one place; cheap navigation; controllers rebuild in `OnEnable` |
| `UIScreenController` base class for screen controllers | Centralizes full-screen, chrome (Header/Sidebar), nav, cursors, config modal — removed ~60% boilerplate |
| SQLite as the save/state store | Sim data is relational (teams/players/games/stats); template DB gives fast, consistent new games; avoids JSON save parsing |
| Static utility classes for simulation rules | Stateless, testable helpers; controllers call them directly |
| No event bus; DB-messages + static hand-offs | Simplest possible decoupling for a single-player sim; avoids async complexity |
| `overall` always recomputed from 11 attributes (cap `potential`) | Single source of truth for ratings; training/aging stay consistent |
| **`schema_migrations` + `PRAGMA user_version`** for data migrations; column-presence `ALTER TABLE` for schema | Migrations live with the slot (delete slot = clean state); additive schema keeps old saves openable |
| Background work via `Task.Run` + WAL + `AsyncLocal` ambient connection (`RunInBackground`/`RunInBackgroundAsync`) | Heavy batches (injuries/physical, `StartNewSeason`, AI trades) off the main thread; match sim stays main-thread (fast, stable) |
| Cap constants in `TradeHelper` and `league_settings` | `TradeHelper` is the 2026-27 fallback for const parameters; the live source is `CbaTable` + `league_settings` (seed and rollover apply the season row; no +5% blind growth). |
| **Minutos de rotación en `team_lineup.rotation_minutes`, no en `players`** | La convocatoria es la fuente de verdad (Quinteto y Rotación comparten `team_lineup`); al cambiar de equipo o irse a FA los minutos no viajan con el jugador. El `-1` es el único centinela de "automático" — `0` es un valor real (0 minutos). |
| **Imágenes de equipos por overlay (`TeamImages`)** | Los logos/pabellones originales viven en `Resources` (solo lectura, empaquetados); las versiones personalizadas se guardan en `persistentDataPath/TacticalFive/Custom/{scope}/...` (`Logos/{size}`, `Arenas`, `PlayerPhotos`) y tienen prioridad al cargar. **Lógica de ámbitos en `CustomScopes`** (`Active`, `ScopeRoot`, `HasCustom`, `CopyCustom`, `DeleteScope`, migración); `TeamImages` la usa para `Logos`/`Arenas`. **Ámbitos por partida:** `scope` = `template` (lo que edita el Editor) o `save_{n}` (partida). `InitTemplateSession()` fija `template`; `InitSaveSlot(n)` fija `save_{n}` y, si la partida es nueva (o antigua sin carpeta), hace snapshot copiando `template → save_{n}` (`CopyCustom`, que siempre crea la carpeta destino). Al borrar partida (`GameSaveManager.DeleteSave`) se borra `save_{n}`. Migración una vez: si existe la carpeta global antigua `Custom/{Logos,Arenas}` se mueve a `Custom/template/`. RESETEAR solo borra el ámbito `template` (`ClearCustom`); las partidas existentes conservan las suyas (las originales nunca se tocan). Todas las cargas de `Teams/Logos`/`Arenas` pasan por `TeamImages` (`Logos`/`Logo`/`Arenas`/`Arena`, que usan el ámbito activo); para leer varias partidas a la vez existe `LogosFor`/`LogoFor`/`ArenasFor`/`ArenaFor(scope, ...)` (la caché está indexada por ámbito), y la pantalla Cargar Partida usa `SlotScope(slot)` = `save_{n}` si tiene carpeta, si no `template`. |
| **Foto de jugador por ámbito (`PlayerPhotoHelper`)** | La foto custom se guarda en `Custom/{scope}/PlayerPhotos/{id}.png` (mismo sistema de ámbitos/snapshot/borrado que logos/pabellones) y tiene **prioridad sobre `Resources`** al cargar (`Load`): custom → `Resources/{id}` → `Resources/{photoField}` → `PlayerPhotos/{slot}` → `PlayerPhotos/{id}` → `default`. El Editor la cambia en la pestaña JUGADORES (`ValidatePhotoFile` PNG 64–2000 px + `SetPhoto`). |

## 6. Confirmed assumptions

- `overall` es la media redondeada de los 11 atributos capada por `potential`, calculada **solo** por `PlayerRating.FromSum`/`FromAttributes` (fuente única). Seeder, G-League, draft, desarrollo y mentoring recalculan con ella (`RecalculateOverall()`); no la dupliques.
- **Escala de atributos:** 1–99 es el rango legal universal para los 11 atributos. Valores `<25` pueden ser debilidades posicionales intencionales (en el snapshot, sobre todo blocks), no un defecto ni algo que haya que subir. `PlayerAttributeScale` centraliza el rango; el suelo 30 de generación y el suelo 25 de estimación de scouting son límites de proceso separados. Mutaciones como edición/progresión deben conservar el rango legal.
- **Media y estrellas del equipo:** media aritmética de los `overall` canónicos de todos los jugadores con `team_id` (la población de `GetPlayersByTeam`), no solo quinteto ni 15 estándar. Es descriptiva; no hay objetivo 85. `PlayerRoleRules.FromOverall` asigna Estrella individualmente desde OVR 90; **se permiten varias estrellas por equipo**, no hay límite de unicidad. En el snapshot F1-03, medias de 72,38–83,36 (media simple 76,83), 18 jugadores ≥90; NYK/PHI tienen 2, OKC 3. Estas cifras describen el snapshot, no son targets.
- **Fuente del roster inicial:** `DatabaseManager.Seeding.cs` (`SeedPlayers` y `SeedFreeAgents`) declara los jugadores con los que empieza la partida. El usuario mantendrá esas listas manualmente cuando cambien las plantillas; el total actual (519 asignados + 120 agentes libres = 639 jugadores, snapshot 2026-10-24) no es una cuota permanente. Puede añadir/quitar jugadores y actualizar sus fotos. **Trevon Brazile (id 134) permanece en DEN**; no reasignarlo para cuadrar plantillas. RayJ Dennis usa el id 611 y Tristan Enaruna el 612.
- **El tamaño de plantilla no se valida:** 14–17 (`TradeHelper.MAX_ROSTER` = 17; mínimo jugable 12) es la referencia de juego, no una regla del seed. El auditor de seed **informa** (`RosterOutOfRange`) pero no emite hallazgo por ello, y no existe fuente externa de plantillas: **nunca reasignes jugadores reales para cuadrar conteos**. Los desvíos actuales (ATL 18, DEN 18, PRT 13) son un ajuste manual opcional del usuario.
- **Salario mínimo del seed:** desde F4-08 el suelo es el mínimo universal de 0 años (`CbaTable.MinimumSalary`, $1.357.763 en 2026-27) y los contratos nuevos deben respetar la banda de experiencia (0/1/2/3+). Los contratos sembrados bajo el suelo interno anterior de 2 M se conservan como **legacy** (el auditor los cuenta como informativos, no como error) y se regularizan al renovar; los 14 que estaban por debajo de 2 M ya se corrigieron en F1-04. No reasignes jugadores para cuadrar conteos.
- **Template auto-reparable antes de clonar (F1-08):** `EnsureTemplateDb` compara `db_meta.seed_fingerprint` con `SeedBaseline.Fingerprint`, valida lo que realmente clona (teams/players/settings; no G-League) y reconstruye template viejo/corrupto en temporal, con `.bak` y replace atómico. La G-League se siembra por slot. Un template recién construido o el slot final con ERROR sigue bloqueando y revirtiendo; no degradar invariantes a WARN. **La huella es frescura, no validez:** el build siembra → audita → sella → publica, y una huella distinta solo avisa (con el hash nuevo) y reconstruye; el test de EditMode es quien exige actualizar la constante. Al cambiar teams/players/league_settings, actualiza la constante tras revisar el seed.
- **Contratos revisados F1-04 (2026-27):** se usaron cap hits para que `players.salary` (campo único que el juego utiliza en nómina/cap) se compare con los aprons. Embiid: $57,985,752, contrato de 3 años (2 garantizados + PO), extensión máxima firmada 2024 (el seed de 2026-10-24 lo tiene en **$58,100,000** por edición del usuario; el test `ContratoEmbiid_ReflejaCapHitMaximo2026_27` fija el valor del seed, no el cap hit verificado). Houston seed: $207,164,502 después de corregir los 13 cap hits con dato verificable; tres entradas sin contrato activo en 2026-27 se conservaron a petición de no alterar el roster. El offset interno de +$20M que citaba F1-04 se retiró en F4-07: el 2.º apron vigente es el oficial 2026-27 ($221,686,000) y Houston queda $14.5M por debajo.
- **Modelo de posesiones del motor (F2-01/F2-02):** la posesión es la unidad que alterna y **no hay azar** en quién ataca. `PossessionState.BeginPeriod(n)` da el saque al equipo que no abrió el periodo anterior (Q1 local, Q2 visitante, Q3 local, Q4 visitante, prórrogas alternando) y `NextPossession()` lo cambia al cerrar cada posesión; un rebote ofensivo **no** cambia de dueño (`RunPossessionChain`, tope `MAX_ATTACKS_PER_POSSESSION` = 4, que produce las segundas oportunidades). `PossessionTally` distingue posesiones de ataques y se expone en `GameResult.possessions` (diagnóstico, no se persiste). No reintroduzcas monedas por posesión ni por cuarto.
- **Faltas y tiros libres (F2-03):** `FoulState` lleva las faltas de equipo del periodo (se reinician en cada periodo) y `DefenseFouls.RegisterFoul()` cuenta la falta del que defiende y devuelve si deja al rival **en bonus** (4.ª falta de equipo; 2.ª en `IsClutch`, últimos 2 min del 4.º cuarto y de las prórrogas). La falta sin tiro en la penetración da 2 tiros libres en bonus y, si no, el ataque continúa sin consumir posesión. Los libres se tiran **solo** con `ShootFreeThrows` (no inventes otro `ftPct`): si el último se falla, `AttachLiveRebound` resuelve el rebote con `DoReb` y un OREB mantiene la posesión. La 6.ª falta expulsa (`EjectFouledOut` con relevo por encaje posicional/minutos/OVR); `PickSubstitution` no puede reinsertar a un expulsado. Sin banca el equipo sigue con cuatro.
- **Atributos con efecto propio (F2-04/F3-04):** los once atributos llegan al `PlayerStatSnapshot` (`InitPS`). `speed` = ritmo (`SpeedPaceDelta`, `(media de ambos equipos − 70) × 0,15` posesiones; pace base 96), `dribbling` = pérdidas (`BallSecurity` = bote medio de PG/SG/SF en pista; `TurnoverChance` base 0,147, resta `(bote − 70) × 0,0015`, acotado 0,02–0,30), `athleticism` = finalización (`FinishingBonus` 0,0018 al TC2) y rebote (`ReboundAthleticismFactor` 0,7–1,4 en `ReboundWeight`), `iq` = selección de tiro (término `(three_point − shooting) × 0,0015 × iq/100` en `ShotType`). La conversión de tiro usa pendientes calibradas alrededor de media OVR (2P `0,5165 + (shooting−70)×0,0025`; 3P `0,400 + (three_point−70)×0,0035`). Ambos equipos usan rebote `reb^3`; el ataque escala `×0,42` (sin desigualdad de exponente). **No vuelvas a calcular pérdidas, ritmo o TC de dos con fórmulas ad hoc en `RunPossession`:** usa esos helpers (fuente única) y no añadas un segundo término de ritmo fuera de `SpeedPaceDelta`.
- **Box score = suma de acciones (F2-05):** no hay pisos artificiales de asistencias/rebotes/robos/tapones. `SimulateGame` **no reescribe** ninguna estadística después de simular; el `rating` y los dobles-dobles salen de las cifras reales. Invariantes a preservar: asistencias ≤ canastas del equipo, tapones ≤ fallos del rival, robos ≤ pérdidas del rival y rebotes ≤ fallos + libres fallados. Si un atributo parece «no llegar» a sus líderes, se corrige el peso de la jugada (Fase 3), **nunca** con un mínimo garantizado.
- **Plantilla corta sin marcador inventado (F2-06):** con **1–4 sanos** `SimulateGame` juega con los disponibles y el box score sale de la simulación real (`GameResult.shortRoster`); solo sin **ningún** jugador sano se resuelve por **incomparecencia 0–20** (`GameResult.walkover`, sin `player_game_stats`, sin fatiga ni lesiones; si ninguno se presenta gana el local 20–0). El aviso al jugador lo emite `DashboardController.NotifyShortRoster` (`NewsType.PLANTILLA_CORTA`, categoría CLUB, All-Star excluido). No reintroduzcas el `Random(105..126)`/`Random(100..121)`.
- **Play-by-play solo si se ve (F2-08):** `SimulateGame(..., capturePlayByPlay)` — en modo directo la crónica es `null` y `PlayPossession` no llama a `CaptureBox`/`DiffBox` (antes se calculaba entero y se descartaba). `DashboardController` pasa `game.game_type != "allstar" && GetSimMode() == 1`; G-League, postseason y tests usan el default `false`. No vuelvas a construir deltas incondicionalmente.
- **Persistencia del partido en lote (F2-09):** `SimulateGame` **no** hace un `Update` ni un `Insert` por jugador. Usa los `PlayerData` que ya recibe (`playersById`), acumula físico/lesiones en `changedPlayers` y las filas en `statRows`, y escribe al final con `DatabaseManager.UpdatePlayersBatch`/`SavePlayerGameStatsBatch`. Los dos helpers usan `bool own = !_db.IsInTransaction`: dentro de la transacción del día escriben en ella y **nunca anidan `BEGIN`**. No vuelvas a meter `GetPlayerById`/`UpdatePlayer`/`SavePlayerGameStats` en los bucles del postpartido.
- `PlayerData.id` manual (seed 1..~600) — stable across cloned slots.

- Employee `reputation` (1–5) drives ticket multiplier and renovation discounts (not `skill`; `EmployeeData` has no `skill` field).
- FA external signings have **no Bird Rights** (`birdMax=0`); exceptions apply by apron when over cap.

- **Pantalla ROTACIÓN (`GameScreen.Rotation`, submenu PLANTILLA tras QUINTETO):** reparto manual de los 240 minutos del partido entre los 12 convocados (`RotationController`, `UI/Screens/Rotation/`). Persistencia en **`team_lineup.rotation_minutes`** (`-1` = automático, `0..48` = fijo); `PlayerData.rotation_minutes` es **transitorio `[Ignore]`** rellenado por `GetActivePlayers` para que el simulador lo use como `target_minutes` (`PrepareRotationMetadata`: si es `< 0` aplica la heurística `GetTargetMinutes`; si está configurado es **vinculante**, con suelo de **2 min** —`0` se respeta: no juega— y sin penalización por fatiga). **Los minutos configurados se respetan de verdad** gracias a `GameSimulator.PickSubstitution` (helper puro; sale el que más se pasa de su plan, entra quien tiene minutos pendientes ponderando encaje posicional ×1.0/×0.85/×0.6; nunca reingresa a quien agotó su plan si hay relevos con minutos; nunca deja la pista sin interiores) y a ventanas de substitución densas cada 1,5' (las usa cualquier equipo con plan de minutos; solo la G-League y el All-Star conservan el calendario antiguo). Si nadie tiene minutos pendientes no hay cambios (los de pista completan cuando la suma < 240); si el total configurado es 0, el equipo vuelve al reparto automático. SUG. = `GameSimulator.GetSuggestedMinutes`. **Desde F2-11 la IA también juega con un plan de minutos:** si un equipo no tiene minutos configurados, `PrepareRotationMetadata` reparte los 240 con `GetAutomaticMinutes` (rol + nivel + forma física) y `RotationPlanner.AutoAssign`, marca `planned = true` y el simulador lo respeta con las ventanas densas y `PickSubstitution` igual que el equipo del usuario. ## 7. Things that must NEVER change without reviewing the rest of the project

1. **`overall` semantics** (mean of 11 attrs, cap by potential) — affects seed, training, aging, migration, drafting, AI evaluation, standings sorting.
2. **Cap/apron/MLE source** — `CbaTable` + `league_settings` (season row) are the live source; `TradeHelper` constants are only the 2026-27 fallback. Do not reintroduce a +5% rollover or hardcode another season's figures outside `CbaTable`.
3. **`ScreenManager.GoTo` contract** (mode handling, `ShowOnly` SetActive) — every controller depends on it.
4. **`GameResultCache.Clear()` at day start** — forgetting it corrupts the results flow.
5. **Slot/DB path layout** (`TacticalFive/saves/save_{n}.db`, `template.db`, `saves.json`, `PlayerPhotos/{slot}`) — game saves and delete logic depend on it.
6. **`MessageData.sender_type` semantics** (0 system / 1 player / 2 news) — used for filtering/icons.
7. **`player_season_stats` + `monthly_awards` dual creation path** (CreateTable AND raw SQL) — any schema change must update both.
8. **`phase` state machine** (preseason→regular→playin→playoff→finished) — drives dashboard, playoffs, awards. **La G-League NO participa: su postseason se gobierna solo por datos (`game_type` gleague/gleague_playoff).**
9. **The config modal in the base** — `UIScreenController.InitConfigModal`; the 12 controllers that override `RegisterCallbacks()` without `base` don't get it — keep new screens on the base path.
10. **`schema_migrations` / `PRAGMA user_version`** — data migrations are named and stored in the DB (per slot); don't reintroduce global `PlayerPrefs` flags.
11. **Background DB work** — helpers run on the ambient (`AsyncLocal`) connection inside `RunInBackground`/`RunInBackgroundAsync`; don't touch `_db` off the main thread. Tampoco llames a `Application.persistentDataPath` desde un hilo de fondo: resuelve la ruta en el main thread y pasa el string (p. ej. `RebuildTemplateDb(path)`; el overload sin argumentos usa `TemplateDbPath`).
12. **Codificación de ids G-League en `games`** — home/away = id filial + 1000 (`GLeagueHelper.GAME_TEAM_ID_OFFSET`); cualquier query nueva que lea partidos GL debe descodificar con `DecodeGlTeamId`; los prospectos simulan con id +500000 (`PROSPECT_ID_OFFSET`). No "limpies" estos offsets creyendo que son bugs.
13. **`team_lineup.rotation_minutes`** — centinela `-1` = automático; la heurística del simulador (`GetTargetMinutes`) es el fallback. Un valor `≥ 0` es **vinculante** para el equipo del usuario (`fixed_minutes` → `PickSubstitution`), con suelo de 8 min y `0` = no juega. Si cambias el umbral, actualiza `PlayerData.rotation_minutes` (inicializador `-1`), `RotationController.Effective`, `PrepareRotationMetadata`, `PickSubstitution` y `DatabaseManager.SetLineupMinutes`. Los sliders de ROTACIÓN nunca permiten pasar de **240 min** en total (`RotationController.RefreshSliderLimits` → `CustomSlider.MaxValue`): con el reparto completo o excedido cada barra solo puede bajar. **Al crear la partida** (CONTINUAR en Preseason) se siembra la convocatoria (`EnsureLineupSeeded`) y los minutos quedan en automático; en ese estado la pantalla muestra el **reparto automático de 240** (`RotationPlanner.AutoAssign`, suelo 2 = `MIN_FIXED_MINUTES`) y lo fija al primer toque de slider. Las sugerencias por jugador (`GetSuggestedMinutes`) NO suman 240: **la referencia de la pantalla es la cuota de 240** (`RotationPlanner.AutoAssign` sobre los ideales; columna SUGERIDO y ± contra esa cuota, tooltip con el ideal bruto). Tabla de objetivos (`GetTargetMinutes`): titular ≥90 → 40, ≥85 → 34, ≥80 → 33, ≥75 → 26, <75 → 20; suplente ≥90 → 32, ≥85 → 28, ≥80 → 22, ≥75 → 14, <75 → 12; `UltimoRecurso` → 2 (`MIN_FIXED_MINUTES` = 2). El reparto de 240 usa una **rotación corta de 10** (`RotationPlanner.ROTATION_SIZE`: solo los 10 mejores objetivos reparten; el fondo queda en el suelo). El rol se asigna por media con `PlayerRoleRules.FromOverall` (seed, draft y migración `role_from_overall`). **Antes de simular** el Dashboard valida la rotación del equipo del usuario (`RotationPlanner.Evaluate`): es válida si no hay jugables, si está **todo en automático** (todos ≤0) o si suma **240 exactos y válidos**; si no, muestra el aviso ROTACIÓN INCOMPLETA (IR A ROTACIÓN / ASIGNAR AUTOMÁTICAMENTE = `DatabaseManager.AutoAssignRotationMinutes`) y en simulación rápida la pausa. Solo cuentan los convocados jugables (lesionados/G-League fuera).
14. **`PlayerData.rotation_minutes` es `[Ignore]`** (transitorio): nunca añadas una columna `rotation_minutes` a `players` sin revisar quién la rellena (`DashboardController.GetActivePlayers`).
15. **Histórico de carrera por `player_id`, nunca por nombre** (`historical_player_stats`): `>0` jugador real, `-1` leyenda del seeder (intocable), `0` fila antigua sin dueño (solo se adopta en la migración si el nombre identifica a un ÚNICO jugador). Reglas puras en `HistoricalStatsRules` (`RowForPlayer`/`CanAdopt`/`IsLegendRow`/`BuildAdoptionPlan`); la migración usa el plan y **no adopta homónimos**. No vuelvas a resolver carreras por nombre: los pools de nombres solapan con las leyendas (SEA-06).
16. **`playoff_series` se escribe al cerrar cada serie** (`PlayoffsGenerator.AdvancePlayoffSeries`, idempotente por `manager_id+season_id+label`): `games` se purga en el rollover, así que es la **única** fuente de rivalidades (play-in excluido). Agregaciones puras en `RivalryHelper`/`DynastyHelper`; dinastías/prestige se derivan de `season_records` (no añadas columnas a `teams`).
17. **El All-Star no persiste `player_game_stats`** (`SIM-14`): las convocatorias viven en **`all_star_roster`** (`SaveAllStarRoster` en el partido de las estrellas) y son la única fuente de `GetAllStarAppearances` (Palmarés) y de los `award_type="all_star"` de la trayectoria. Las columnas `season_records.all_star_pg..c` son legado sin uso.
18. **Mercado de buyout:** al rescindir, el jugador queda FA con **contrato a 0 y salario = mínimo de su experiencia** (`TradeHelper.MinimumSalary`; `waived_game_day` = jornada de la rescisión) y firma **por ese mínimo y 1 año** (`BuyoutMarketRules.ContractYears`); la IA le firma **en cuanto pasa esa jornada y solo si tiene 75+ de media** (`BuyoutMarketRules.MinOverall`; por debajo queda en agentes libres y decide el mercado general) (destino = ranking contender > balanced > rebuild, menos jugadores en su posición, mejor plantilla y prestigio; **sorteo ponderado entre los 3 mejores postores**, `RankDestinations`/`PickSuitor`, con noticia) y **los fichajes IA usan `CanAISignExternal` (espacio → MLE → mínimo) y fijan el salario nuevo** (nunca heredan el viejo). **Al expirar, el precio pedido sube a su valor de mercado** (`TradeHelper.MarketValueByOvr`) para que no quede barato para siempre, la renovación IA va a mercado si está **3× por debajo** (`ShouldRenewAtMarket`, sin el tope no-Bird → máximo por experiencia) y `ProcessOwnFreeAgentResignings` permite al equipo con **Bird rights** re-firmar a sus FA recientes por encima del tope (límite 2º apron). La marca se limpia al firmar y en el rollover; el equipo que le cortó sigue pagando el resto como `dead_money`.
19. **Hitos de carrera (E1):** `player_milestones` (una fila por hito y `player_id`, sobrevive al retiro). La carrera se calcula como **histórico (`historical_player_stats`, por `player_id`) + temporada en curso (todos los tipos menos All-Star) + honores** (`rings/finals_mvps/season_mvps` y All-Star de `all_star_roster` + `allstar_appearances_seed`) en `DatabaseManager.BuildCareerTotals`. `MilestoneService.EvaluateDay` corre cada día antes del motor de narrativa, registra lo nuevo y emite **una noticia agrupada por jugador** (`NewsType.LEGADO`); la **primera vez por partida** hace una línea base silenciosa (`milestones_baselined`). El hilo `hito_alcanzado` (por jugador, dura el día) **no duplica la noticia**: solo da badge y efecto. El HOF induciendo con **10× All-Star o 3× MVP** es parte de esta feature.
20. **Parte médico (E2/F3-06):** las lesiones viven en `players` (`injury_type`, `injury_days` restantes, `injury_total_days` total, `treated`, `recovery_risk`) + `injury_history` (episodios cerrados). `InjuryCatalog` contiene 27 tipos con gravedad/familia/riesgo; `InjuryHelper` maneja evolución, alta forzada, recaída y progreso. `MatchRiskPerGame` tiene base **0,20 a 36 min** (5 min≈2,78 %, 20≈11,11 %, 44≈24,44 %), proporcional a exposición, ×`1+(30−fisico)*0.15` bajo físico 30, más `RelapseChancePerGame`; 0 min⇒0. Nunca uses probabilidad plana. El sorteo es postpartido. `CanSustainMatchInjury` impide que una nueva lesión deje menos de 5 sanos en la convocatoria simulada. Evolución diaria en el pre-lote (`EvolveDays`), recaídas solo si `recovery_risk>0`, riesgo −25 al descansar/−10 al jugar y desaparece en 0; riesgo pendiente⇒tipo de lesión no vacío.
21. **Economía de mercado (E3):** `teams.market_size` (0-100, migración que rellena por reputación en partidas viejas) + reglas puras en `MarketEconomy` (asistencia elástica `EstimateHomeAttendance`, precio de referencia, `DealValueMultiplier`) y `ContractMarket` (renovación/escala de patrocinio y TV). La asistencia ahora la decide `MarketEconomy` (no la fórmula inline): demanda por mercado/rival/racha/objetivo × factor de precio; la confianza de la afición **solo** pesa en partidos del usuario en casa (`includeFanConfidence`). Los ingresos por partido de patrocinio/TV escalan con fama+mercado. Al expirar un contrato, `StartNewSeason` (`RenewMarketDealsForTeam`) intenta sustituto con prob. `0.45 + mercado×0.35 + reputación×0.20`. No reintroduzcas la fórmula antigua en `CalculateAttendance`.
22. **Día pendiente y pre-lote:** el día que se simula al avanzar es `DashboardController.FindNextGameDay(season, managerId)` (estática: la usan el botón "DÍA DE PARTIDO" y la pantalla de previa). Si rompes esta regla, el "día pendiente" (`DashboardController.FindNextGameDay`) se calcula sobre una fecha equivocada y desaparecen el botón "DÍA DE PARTIDO" y el "IR AL PARTIDO" de la previa.
25. **Nunca anidar transacciones en el seed.** `InitSaveSlot` siembra la partida nueva dentro de `_db.RunInTransaction`; `SeedPlayers`/`SeedFreeAgents` usaban `BeginTransaction()`, que en sqlite-net **lanza** `InvalidOperationException` si ya hay una abierta. En una instalación sin `template.db` eso hacía que el alta devolviera `false` y el menú no hiciera nada (bug del 22/10/2026, cubierto por `SaveSlotInitTests`). Al escribir código de seed o de inicialización: guard `if (_db.IsInTransaction) { ...inserciones... ; return; }` o `bool own = !_db.IsInTransaction` como en `SaveGLeagueGames`/`SeedPlayers`. **Y `InitSaveSlot` genera el template al vuelo (`EnsureTemplateDb`) si falta**, porque `template.db` solo lo creaba el Editor y en una máquina recién formateada no existe.
26. **Ofertas de traspaso de la IA: revalidar al mostrarlas y no dejar esperas sin resolver.** La IA valida el traspaso al generarlo (`BuildOfferPackage` → `TradeHelper.ValidateTrade`), pero la oferta queda pendiente varios días y la nómina/plantilla/hard cap cambian: `DashboardController.ValidatePendingTradeOffer` la revalida **antes de mostrar** (`ShowNextPendingTradeOffer`, descarte silencioso `processed = 2` + log) y otra vez al aceptar. Además, **toda salida de un modal que se muestra con la simulación rápida pausada debe resolver su espera**: los botones de `ShowOfferResultModal` invocan `onFastSimResolved` (bool = ir a Quinteto) porque el flujo de traspasos espera `_tradeOfferModalResolved` (no `_offerModalResolved`, que es el de renovaciones/fichajes). Un `return` sin resolverla deja `_isLoading`/`NavigationLocked` fijados y el juego muerto (bug de auditar: la rama "TRASPASO NO VÁLIDO").

27. **Valoración de traspasos: `TradeValueHelper` es la fuente única (F4-01).** `TradeHelper.ValidateTrade` valida legalidad de salarios/cap/aprons/cupos; no es una fuente de valor. `TradeValueHelper` (puro) valora jugadores (curva OVR × edad × potencial + contrato contra `TradeHelper.MarketValueByOvr`) y rondas (`TradeHelper.PickBonus`). `CheckOffer`/`IsSane` analiza un lado, con `Tolerance(strategy)` = Contend 1,20 / Balanced 1,05 / Rebuild 1,00 y `MaxOvrGap` (+3, ampliable +3 por R1 hasta 2); `CompareOfferSides` entrega ambos lados recíprocos y acepta overrides salariales del S&T; `IsSaneBothWays` queda para IA-IA (banda bilateral1,20). `MarketController` separa `ValidateTrade` de `CompareOfferSides` y toma la decisión de valor desde el club receptor; ya no usa la heurística aleatoria/suma OVR `TradeHelper.EvaluateTrade` (eliminada). **No reintroducir valoraciones ad hoc**: `BuildOfferPackage`, `PickTradeTarget`, `GenerateAITradeOffersForPlayer`, `TryFindAITrade` y los S&T IA usan este helper. `TrySellVeteran` está exento a propósito: fire sale de rebuild entrega veteranos por jóvenes/picks. El cap de contrato usa `GetValueCap()` (crece +5 %/año), no una nueva constante. Tests en `TradeValueHelperTests`.
28. **Aleatoriedad inyectable del partido (F3-01):** `GameSimulator.SimulateGame` recibe `IRandomSource`; `null` usa `UnityRandomSource` y el juego conserva `UnityEngine.Random`. Para reproducibilidad pasar `SeededRandomSource(seed)`; la misma semilla y entradas reproduce marcador, cuartos, box score y crónica. El source debe seguir pasándose explícitamente por todo nuevo camino aleatorio del motor; no llames `UnityEngine.Random` desde `GameSimulator` ni uses estado estático compartido. Calendario, draft y lotes IA en background aún no forman parte de esta garantía.
29. **Laboratorio Monte Carlo (F3-02):** `MonteCarloRunner.Run(config)` corre temporadas sintéticas en memoria con `SeededRandomSource`, sin `DatabaseManager`, UI de juego ni escrituras a saves. Usa **15 jugadores/equipo** (ratings vía `PlayerRating`), calendario round-robin reproducible y no clona el seed ni el calendario de producción.
